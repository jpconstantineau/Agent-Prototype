# Local LLM endpoint with Chrome Prompt API fallback

Status: approved specification added during the Hermes review. Extends the previous Prompt-API-only inference design while retaining its tool contracts, vanilla JavaScript modules, and policy boundary. Uses [runtime contracts](runtime-contracts.md), [agent library](agent-library.md), [compaction](context-compaction.md), and [observability](observability.md). Voice remains [Chrome/browser-only](voice-interaction.md).

## Purpose

Allow a stronger locally served text model while retaining Chrome's Prompt API as a usable fallback. One inference adapter preserves the same browser-owned tool loop, permissions, budgets, and recovery rules across providers.

## User intent

Configure and test a local endpoint, choose model routes and fallback behavior, and see which provider actually handled a run.

## Agent intent

The agent does not act through this spec to configure endpoints, select a more permissive provider, or trigger fallback itself. It returns the same structured actions through the selected adapter; the harness owns routing and safe continuation.

## Outcome and provider boundary

Use a user-configured stronger local model server for text inference, with Chrome's LanguageModel as fallback. The model endpoint proposes the same single tool_call or final JSON action; the browser alone validates/executes tools. Do not send native function tools for server-side execution, install a server, download its models, or give it database handles. No Python/Node daemon, SDK, React, or production dependency is required in the web app: use fetch, AbortController, JSON, and the existing registry.

Introduce a provider-neutral inference adapter rather than duplicating the agent loop. Required operations are prepare(initialPrompts,options,signal), generate(input,responseSchema,manifest,signal), measure(nextPacket), and dispose(). These are application interfaces, not invented Chrome methods. generate returns `{text,finishReason,usage,identity}`; text is the one assistant content string. finishReason is complete/length/failed; usage is nullable typed input/output/context metrics with measured/estimated/unknown provenance; identity records provider/profile/model when known. measure returns supported measured values or explicit estimates/unknown, never pretends an HTTP server is a Chrome session.

The Chrome adapter wraps availability/create/prompt/measureContextUsage/contextUsage/contextWindow/destroy where supported. The HTTP adapter retains an app-owned bounded canonical message ledger and sends the needed messages each call; it must not assume remote conversation retention. serialize requests from that ledger, not a UI DOM transcript. The session manager still serializes generation, compaction, replacement, Stop, and stale-generation rejection across providers.

## Context-window reference (checked 2026-10-28)

The Prompt API has **no single API-wide guaranteed context-window size**. Its specification leaves capacity implementation-defined; the authoritative value for a ready session is the read-only `session.contextWindow`. Chrome also exposes `session.contextUsage` for the context already retained and `session.measureContextUsage(input, options)` for the incremental cost of a proposed input. Re-read these values for each newly created/rebuilt session rather than persisting a fixed Chrome quota. See the [API capacity definition](https://github.com/webmachinelearning/prompt-api/blob/main/index.bs#L2691) and [Chrome session documentation](https://developer.chrome.com/docs/ai/prompt-api#session_management).

A published [first-hand Gemini Nano harness test](https://maresmichael.com/blog/on-device-ai-models-with-a-harness/) reported **9,216 tokens (about 9.2k)**. This is useful planning context for the small-window design, not a Chrome guarantee or a measurement made on this user's device. Do not hard-code 9,216 as a fallback capacity, assume every browser/model version has it, or infer a larger limit from the installed model's marketing specifications. A normal web page cannot increase `contextWindow` by setting this spec's endpoint field `contextWindowTokens`.

| Quantity | Source | Meaning |
| --- | --- | --- |
| Chrome session capacity | session.contextWindow | Actual runtime-reported window for that session |
| Already retained context | session.contextUsage | Includes initial application instructions and accumulated exchanges; it is not the next prompt's full allowance |
| Next input cost | await session.measureContextUsage(nextInput, {responseConstraint: actionSchema, signal}) | Incremental measurement using the actual input and schema; call only when supported |
| Local endpoint capacity | endpoint profile contextWindowTokens plus verified server/model configuration | Operator-configured limit, separate from Chrome and subject to server validation |
| Local output cap | endpoint profile maxOutputTokens | Maps to HTTP max_tokens; it is neither the total context window nor a Chrome context setting |

Budget all active material: application/agent/project/persona instructions, tool definitions and the structured-response schema, loaded skills, memory/recall, current task, retained replies, tool observations, and supported media. They share the available context; “9,216” does not mean 9,216 additional user-input tokens after setup. Use Chrome's own measurement, including the exact responseConstraint, instead of a fixed characters-per-token conversion. API names intentionally describe context units rather than exposing a tokenizer; preserve provider/unit provenance and do not equate an HTTP tokenizer's counts with Chrome's measurements. See the [Prompt API measurement contract](https://github.com/webmachinelearning/prompt-api#tokenization-context-window-length-limits-and-overflow).

For a supported finite positive window W, retained usage U, measured next-input cost N, and an application reply reserve R, the conservative admission test is `U + N + R <= W`. The existing app policy reserves at least `ceil(0.20 * W)`; this is application policy, not a native output-token guarantee. Measure after session preparation so initial instructions are already counted in U; do not add them a second time. Serialize measurement with generation/rebuild so the measurement is not applied to a different session state.

For illustration only, if runtime W is 9,216: the default 70% compaction check begins at about 6,451 units, the 45% post-rebuild target is about 4,147, and a rounded-up 20% reply reserve is 1,844. Initial instructions and required schemas consume part of those amounts. These figures derive from this project's [context policy](context-compaction.md), not additional Chrome limits. A larger endpoint's 24,000-character input cap or memory review's 64,000-character allowance cannot be compared directly to these token/context counts.

Unsupported/missing/non-finite measurements mean Unknown in the UI/diagnostics and require the existing conservative bounded-context path; they never become an invented 9,216 capacity. Record the actual observed window/usage, measurement provenance, session generation, observation time, and known provider/model identity in the session diagnostic payload. Do not invent a model version when Chrome does not expose one. Configuring an HTTP window still does not prove the server accepted that capacity; retain the configured-versus-observed distinction on both routes.

Chrome may evict older conversation pairs when context overflows, preserving its initial system instructions; an input that still cannot fit can fail with QuotaExceededError. Observe contextoverflow and rebuild from authoritative history/receipts before another mutation under the existing compaction rules. Automatic eviction is not semantic summarization. On local-to-Chrome fallback, prepare and measure the required Chrome packet against the **new session's actual window**; compact/select a smaller explicit batch or stop if it does not fit. A stronger maintenance model's larger source packet is never sent to Nano by assuming equivalent capacity. [Chrome overflow behavior](https://developer.chrome.com/docs/ai/prompt-api#session_management).

Acceptance additions: test runtime windows different from 9,216, changing capacity after session recreation, missing/unknown measurements, schema overhead, initial-prompt accounting, reply reserve, overflow events, and larger-local-packet fallback. No model download, test inference, or machine-specific capacity measurement is required merely to document this reference.

## Device-local endpoint configuration

Settings contains a device-local model route `{routeId,revision,label,primary:'local_http'|'chrome',endpointProfileId:ID|null,fallback:'automatic'|'ask'|'off'}`. Defaults for an unconfigured device remain Chrome; after explicit local setup choose local_http with automatic fallback unless the human chooses otherwise. Agent main/subagent configurations may reference a routeId or inherit the device default. A route selects inference only; it never changes tools, skills, projects, memory, permissions, or run budgets. Unresolved routes on another device show unavailable and follow the explicitly saved fallback policy.

An endpoint profile is closed `{profileId,revision,label,baseUrl,model,protocol:'openai_chat',schemaMode:'json_schema',contextWindowTokens,inputCharLimit,maxOutputTokens,timeoutMs}`. label 1–80, baseUrl <=500 absolute URL, model exact nonblank 1–200, contextWindowTokens integer 1024–131072, inputCharLimit 2000–200000 default 24000, maxOutputTokens 256–8192 default 2048 and less than half the configured context window, timeoutMs 5000–180000 default 90000. These are operator-configured limits, not proof the model/server supports them. Connect test must validate actual behavior; never infer capacity from a model name or self-description.

V1 accepts loopback HTTP/HTTPS endpoints, plus explicitly entered LAN HTTPS endpoints approved by the human. No model-provided endpoints, public cloud endpoints, URL userinfo/query/hash, automatic network scanning, arbitrary custom headers, or redirects to another host. baseUrl ends in /v1/; form the one chat/completions path through URL resolution and recheck the origin/path. URLs, server model choice, and endpoint tokens stay device-local and are excluded from ordinary agent exports/sync. An optional bearer token is entered only in direct Settings, kept in memory for the page session, and never sent to a model/log/export. The declined agent credential-request tool is not reintroduced.

A local address alone cannot prove the server/model keeps data local; an operator could configure a cloud-backed model or proxy. Show that boundary and require a locally served model/server configuration. Do not silently call a hosted provider through a compatible endpoint. The app never forwards voice input/output to this route in v1, even if the server exposes audio APIs.

## Browser connection and capability test

Use a secure app context, explicit Connect/Test from a user gesture, CORS fetch with credentials:'omit', cache:'no-store', redirect:'error', timeout/abort, and an exact allowed origin. The local service must allow the actual app origin and required POST/Content-Type headers; a successful curl request does not prove browser access. Handle Chrome Local Network Access/mixed-content restrictions as browser capabilities. Where supported, explicit loopback address-space request options may be used according to current definitions. Unsupported permission-query names/options are not hard-coded prerequisites. Never recommend disabling browser security, wildcard credentialed CORS, opening the service to every network, or assuming no-cors produces readable JSON.

The hosting page's CSP connect-src must permit the chosen endpoint; a client cannot bypass a restrictive response header. Report CSP blocking with available browser diagnostics and offer Chrome instead. Do not add an unrestricted network proxy or broad endpoint discovery to work around configuration failures.

The UI shows Disconnected/Testing/Ready/Blocked/Unavailable, selected model and origin, server setup guidance, current browser errors, and Use Chrome. Fetch often cannot distinguish CORS, denied local-network access, TLS, and an unreachable service; show an honest diagnostic instead of inventing the cause. No remote proxy/Azure relay is included. LAN HTTP can be considered in a later adapter after its browser/security behavior is explicitly specified.

Connect sends harmless fixed test messages only, first with a simple closed JSON schema and then representative actual action schemas (including nested arrays, enums, const, null, anyOf, additionalProperties:false). A model that ignores/rejects the required schema vocabulary is incompatible with this profile. Probe results are cached by endpoint/model/profile revision, not permanent proof of every later response. Test a small actual action-schema sample whenever admitted schema structure changes; normal response validation remains mandatory. A text-only server can be Ready without media support; do not advertise image/audio capabilities it has not demonstrated.

## HTTP structured-output contract

POST to baseUrl + chat/completions with JSON body containing model, messages, stream:false, n:1, max_tokens:maxOutputTokens, and response_format. messages contains a first system message with current assembled application/configuration instructions, then canonical accepted user packets and assistant action text. Tool observations remain explicitly labeled user-role JSON data packets as in the shared contract. Omit tools, tool_choice, tool execution plugins, provider secrets, and arbitrary extra parameters.

response_format is `{type:'json_schema',json_schema:{name:'agent_action',strict:true,schema:responseSchema}}`. responseSchema is the exact current admitted action schema, compiled only through a tested semantics-preserving adapter if needed. Do not replace a rejected union/schema with unconstrained text or silently remove fields. A server accepting only a different schema dialect needs a separate tested protocol adapter, not guessed retries. OpenAI-compatible is a protocol label, not a promise of universal compatibility.

```json
{"model":"selected-local-model","messages":[{"role":"system","content":"Return exactly the requested JSON object. This is a harmless connection test; no tools execute."},{"role":"user","content":"Reply with a final message saying ready."}],"stream":false,"n":1,"max_tokens":512,"response_format":{"type":"json_schema","json_schema":{"name":"agent_action","strict":true,"schema":{"type":"object","properties":{"type":{"type":"string","const":"final"},"message":{"type":"string","minLength":1,"maxLength":4000}},"required":["type","message"],"additionalProperties":false}}}}
```

Accept only a successful JSON HTTP response <=1 MiB, one choices entry with index 0, message.role assistant, message.content nonblank string <=48000 characters, no native tool_calls/function_call, and finish_reason stop. Ignore unrelated provider metadata; never expose reasoning_content or hidden reasoning fields as chat/logged model text. A refusal, length cutoff, empty content, non-JSON/HTML error, multiple choices, or unsupported finish reason is no executable action. Parse message.content once, validate against the captured exact app schema, and recheck policy before dispatch. The HTTP envelope may have extra metadata; the contained application action remains closed.

```json
{"choices":[{"index":0,"message":{"role":"assistant","content":"{\"type\":\"final\",\"message\":\"ready\"}"},"finish_reason":"stop"}],"usage":{"prompt_tokens":40,"completion_tokens":10,"total_tokens":50}}
```

Usage fields are optional nonnegative safe integers when supplied; missing is Unknown. Provider token counts and Chrome context units are separately labeled. Do not conflate cumulative transmitted tokens with retained context usage or infer cost. Exact raw action content and sanitized envelope metadata are logged; auth headers never are.

## Context budgeting and fallback

The [Plan/Act extension](plan-act-modes.md) can select independently configured planning and execution routes. Switching from a larger local planner to Chrome requires a measured bounded handoff retaining exact human constraints, phase/rule sources, and receipts; it does not raise Chrome's actual context window or reset call budgets. [Conditional guidance](conditional-instruction-rules.md) and [team](agent-team-coordination.md) context remain scoped across either route. [Completion-report](completion-reports.md) claims require actual evidence under both providers, not a model-specific verified flag.

The approved [structured processing](structured-processing.md), [memory review](memory-consolidation.md), [recall](context-aware-recall.md), and [diagnostic agent](observability-agent.md) extensions may select a human-configured helper route independently of conversational inference. They pass their exact approved output schema through the same adapter under an explicit inference purpose/schema name; agent_action remains the parent loop protocol. All auxiliary content is data and never dispatches as a tool action. Each feature defines bounded input and counted attempts. In particular a larger memory-review packet must fit Chrome before fallback; otherwise show a smaller-batch/model choice, preserving all required evidence rather than silently truncating it.

Preserve shared instruction/skill/result/iteration limits even when a larger model is available. Use configured context window plus any verified provider tokenizer/usage capability; generic chat compatibility supplies no exact preflight tokenizer. inputCharLimit is a conservative application bound, labeled estimated, not a token guarantee. Reserve output room; on context-size rejection compact/rebuild at a safe boundary or stop. The server must be configured to reject rather than silently truncate required instructions/context. Verify this operator behavior during integration; do not claim a generic client can detect every server-side truncation.

Automatic fallback is allowed only at a safe inference boundary for unavailable/timeout/service-capacity/incompatible-schema preparation failures, with no unsettled domain write or pending human interaction. Auth/permission refusal, invalid tool arguments, domain-tool failures, cancellation, and exhausted budgets are not reasons to switch models or bypass a denial. A malformed model action gets at most one correction within the existing call budget; repeated schema failure may hold for explicit provider choice rather than thrash. Count every attempted normal generation, including failed/fallback attempts, toward the main/child call limit. Connect tests are separately bounded to three harmless calls per human Test action.

On fallback: record reason and both provider identities; invalidate the failed generation so late HTTP data cannot dispatch; persist the last settled tool observation and exact operation receipts; build a new Chrome session with current configuration/policy/project, permitted memory/skills, authoritative manifest, and bounded recent context. Measure the smaller Chrome budget before activation. If forced content cannot fit, hold with a visible selection/shortening action rather than silently dropping constraints. If Chrome needs user activation/download, show Enable Chrome and Continue. Fallback never promises a working model where the device lacks it.

If configured, [persona guidance](agent-personas.md) is reconstructed from the same pinned source revision on both routes and included in measured context. Fallback does not silently select, omit, or rewrite a persona; oversized required guidance follows the same visible budget-conflict path. Style adherence may differ by model, but policy, JSON validation, and real execution receipts remain application-owned.

Continue from the next inference boundary once, with the prior operation facts and original user intent. Do not replay historical tool calls, move an absolute reviewed schedule, reset run limits, or reuse consumed approval tokens. Ambiguous tool transport outcomes must be reconciled separately before any fallback. A timed-out HTTP inference has executed no browser tool, because the app did not dispatch its unseen response; abort and discard its eventual response. A local server must be inference-only for this assumption to hold.

Show the active provider/model badge and a visible fallback marker on the run; automatic does not mean hidden. In ask mode stop with a user choice before creating the replacement; off means report the primary failure. Provider choice during an active question/approval is deferred until it settles/cancels. Returning from fallback to the primary occurs only at a new run or explicit idle user switch, avoiding repeated oscillation. Children/maintenance use their configured route under the same queue/scope/budgets; Chrome-only transcription is exempt from this text route by design.

## Integration and acceptance

Add inference-provider.js, chrome-provider.js, local-http-provider.js, provider-profile-store.js, and a Settings connection view. Refactor AgentLoop to request generation/catalog snapshots from the session manager rather than raw session.prompt; the question broker and task executor remain provider-independent. Compaction can use the selected text provider with a tool-free bounded summary contract and its maintenance limits. Clone/retained context are Chrome implementation details, not required HTTP capabilities.

Test request serialization, exact action schema, HTTP size/timeouts, CORS-like failures, credentials omission, token redaction, wrong finish reasons/native tool_calls, Stop/late responses, context estimation labels, and provider pinning. Script a local failure -> Chrome rebuild -> next-step continuation after a committed mutation and prove no duplicate mutation, permission widening, or budget reset. Native integration tests require an explicitly configured real local server and browser origin permission; mocks cannot certify its locality, CORS, tokenizer, schema enforcement, or model quality. No actual server connection is required merely to write this spec.
