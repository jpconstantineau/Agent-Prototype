# HTML and CSS component framework

## Purpose

Turn the reviewed shadcn/ui and daisyUI core component catalogs into original, dependency-free examples governed by this project's palette, typography, density and per-declaration audit. Clearly distinguish a complete native interaction from a styled presentation and a limited alternative. Every included family has public CSS classes, exact HTML, purpose, user intent and a live specimen.

## User intent

Find a suitable component, inspect it in the chosen appearance/density, and understand what it actually does. Use native keyboard/touch behavior without hidden component code, accidental application writes, color-only meaning or an inaccessible imitation of a richer widget.

## Agent intent

Implementation agents read the coverage classification and exact HTML contract before composing UI. They preserve native semantics and the stylesheet's purpose/intent mapping, then add application behavior through the appropriate app specs. Runtime agents gain no new tools or data access from these classes. A styled button, file chooser, progress ring or dialog cannot itself authorize a tool action, read a file or certify success.

## What CSS-only means here

The original shadcn/ui packages are React components, including adapters for behavioral primitives; they are not a standalone CSS component library. daisyUI supplies CSS classes, but a painted component can still depend on its host for state, data and behavior. This catalog evaluates which UI patterns can be implemented with original HTML/CSS and browser-owned behavior. It does not import either library, Tailwind, React, upstream bundles or their default color themes.

[COMPONENT-CATALOG.md](COMPONENT-CATALOG.md) records every name in the reviewed core catalogs: 66 shadcn/ui names and 68 daisyUI names, reviewed 29 October 2026 (daisyUI 5.7.50). Duplicates become 96 families. The 87 included families have one canonical example each; nine full widget engines are classified as requiring script. This is an exhaustive map of those dated core inventories, not every variant, community package, form adapter, chart integration or separate AI extension. Existing chat, code and disclosure primitives can serve those integrations when their application contracts are implemented.

| Classification | What the example promises | What it does not imply |
| --- | --- | --- |
| presentation | CSS appearance/layout for explicitly supplied content | Data retrieval, truth, event timing, writes, timers or persistence |
| native | Real browser-owned behavior through semantic HTML | Async workflows, server checks or an invented application result |
| alternative | A specifically labelled native/presentation subset of a richer concept | Full behavioral equivalence to the upstream widget |
| script | The full widget needs a state/behavior engine; no fake runnable shell is supplied | That its visual primitives cannot reuse the existing CSS |

Examples of limited alternatives: native date input rather than a custom calendar; datalist rather than a constrained async combobox; a single native OTP field rather than scripted character slots; ordinary popup links rather than an ARIA application menu; radio panel choices/link navigation rather than an ARIA tabs widget; scroll snap rather than a looping carousel; CSS pointer resizing rather than a keyboard split pane; paired comparisons with an optional native pointer-resize wipe rather than a full keyboard range/drag engine. Static countdown digits do not tick; a toast layout does not spawn announcements. These limits appear beside each live example and in the exact contract.

## Composition and public classes

Use the exact class/HTML combination from COMPONENT-CATALOG.md. A class alone cannot provide the required semantic element, labels, IDs or browser attributes. Reuse the shared stylesheet baseline, root tokens, native focus treatment and density profiles; extracting one rule without its dependencies is not the supported API.

Public component classes use ui- names; supporting modifier/part classes appear in the exact HTML. Existing .ui-prose is reused for typography. New rules have catalog- decision IDs and the catalog verification family. Existing application/prose rule objects and palette values retain their values. The new .ui-button primary variant composes .btn-primary to retain its written-label contrast exception and forced-color behavior; secondary controls use the ordinary visible boundary contract. No new brand or status colors are added.

The gallery has one shrinkable grid track and cards with min-inline-size:0. Long source/code belongs in bounded scrolling regions, rather than widening every example. The optional comparison wipe uses a container-relative duplicate image and the native CSS resize handle; complete labelled versions remain outside the clipped duplicate as the keyboard/touch-readable alternative. A component owns its explicit dimensions and outside margins: mockup figure margins are reset so native 40px figure offsets do not add to its width. Ordinary target clearance, panels and gaps consume the existing density tokens. Single-pixel boundaries, text size, focus and structural aspect ratios remain protected. Coarse/hybrid/no-pointer targets retain the established 44px-at-default-root minimum.

Navigation bars, footers, docks, corner actions and notifications stay in flow or inside a labelled sample containing block. They do not install viewport overlays or permanent chrome. Adopting a fixed viewport layout later requires an app layout decision that protects focus, software keyboard clearance and document space. The optional aura, mask, mockup, tilt and rear-stack treatments are explicit reference examples, not a change to the quiet default HMI-inspired app philosophy. Masks never crop essential text/images; rear stack planes contain no hidden meaningful content; tilt moves no interactive target.

## Native behavior and accessibility ownership

Use native fieldset/legend/label, checkbox/radio checked state, select, range, date, textarea, file input, progress, details/summary and real anchor destinations. Do not duplicate native state with stale aria-checked/aria-expanded or disguise a role=button div as a real control. Each applicable control has a persistent name and governed focus. Summaries have explicit focus and forced-color overrides because they are native controls outside the earlier global button/input focus selector.

Exclusive accordion opening comes from the details name attribute. Filters use native radio/reset plus :has only over a bounded set of preloaded sample records; they do not query IndexedDB or invent a count. Radio panel choices retain native group semantics and have no tab/tablist roles. CSS cannot implement the expected ARIA tab selection and roving-focus contract. Folder tabs clip the native radio paint while preserving focus and selection; :has(input:focus-visible) draws the protected 3px/3px perimeter around the complete label, with a system-color override. Native arrows select a panel; linked folders remain real destinations. Toggle-style labels retain visible native checks instead of pretending to be aria-pressed buttons. Rating labels use real outlined/filled star glyphs with explicit one-to-five accessible radio names; CSS fills the chosen star and all earlier stars. Native marks remain visible and there is no automatic write. Code and scroll regions are named, focusable and use platform scrollbars; content remains readable without pointer-only resizing.

## Semantic variants and corrected component presentation

The shared modifiers .ui-tone--success, --error, --pending, --info and --neutral resolve --ui-accent to the existing success, danger, warning, interactive and muted roles. Every spelling uses the full ui-tone prefix in HTML. They follow all four palettes without introducing more brand colors. Focus retains its dedicated keyboard role; it is not an alert status. Written labels accompany every status hue. A color preference improves distinction but does not guarantee identification for every color-vision deficiency.

Alerts use bounded accent fills and the mode-dependent on-interactive ink, now explicitly checked at 4.5:1 against all five accent fills. Dark fills use dark ink; light fills use white. Alert dialogs repeat the fill in the heading and the accent on the outer start edge, while their native Close control stays on the neutral dialog plane so ordinary focus contrast remains valid. Aura examples use matching static colored frames with neutral reading fields; the 4px normal / 3px compact notice stroke keeps their accents visible. No status animation or focus imitation is implied.

Avatars use filled discs with the same checked ink and adjacent names. Their example colors distinguish identities and do not assert a person's state. Badges have a 10px dot; status indicators have a 12px dot. Both keep their written labels, preserve the mark under wrapping and use the shared accent variants. Dots and aura decoration provide no sole source of information.

Breadcrumb levels center plain current text, parent links and small aria-hidden slash separators on the same vertical line. Numerical pagination has square governed targets, descriptive page names and a noninteractive current number; the three specimen destinations are real reference documents. It does not simulate fetching result pages.

The conversation specimen has two source-ordered turns. The outgoing turn aligns to the logical end with a checked blue fill and contrasting ink; the reply aligns to the logical start on the neutral support plane. Both retain explicit authors and timestamps, a 65ch maximum measure and a related-content gutter. Alignment and hue supplement author identity without supplying its only meaning.

The skeleton border animation is optional, off initially and enabled only inside .ui-motion-preview when its native .ui-motion-enable checkbox is checked. It varies the border slowly between checked neutral and interactive colors over two seconds each way, leaving text, fill and layout stationary. Written loading information remains outside the aria-hidden placeholder. Unchecking stops it; prefers-reduced-motion disables it even when checked. The spinner uses a protected 3px ring and a 24px diameter at the default root in both densities: shrinking this stroke made the loading segment difficult to see. The same opt-in and reduced-motion rules continue to apply.

Chrome's command/commandfor attributes open and close native dialogs, including an alertdialog presentation, an edge drawer and a lower sheet. autofocus is on the safe Close button, Escape dismisses, and native focus returns to the invoker. These samples close only; they never save/delete or claim approval. Actual confirmation handling must validate the result through the application's receipt/permission contracts.

Popover examples use native popover/popovertarget, implicit CSS anchor placement and flip fallbacks. Navigation popovers contain ordinary links, not fake menu roles. Tooltip/hover-preview use interestfor plus an explicit click route. The tooltip has noninteractive text and aria-describedby; required help also stays visible in the document. Native interest handles hover/focus, persistence while inspecting the target and Escape. A richer preview containing links is a nonmodal support surface, not role=tooltip. No component manually traps focus or synchronizes aria-expanded.

The catalog targets current Chrome, verified with installed Chrome 155. Declarative dialog commands shipped in Chrome 135; native interest support is present in the tested browser and has limited cross-browser availability. Before adopting these components outside that target, check commandForElement and interestForElement on HTMLButtonElement.prototype and CSS.supports for the anchor/typed-attr rules. The gallery adds no JavaScript polyfill. Clicking the explicit popover trigger remains useful when hover interest is unavailable but popovers are supported; environments lacking the required native behavior need a reviewed fallback, not a claim of universal support. CSS-only means no authored component script, not that CSS implements the browser's built-in behavior.

## Values, announcements and safety

Content in examples is explicitly supplied/fictitious. Application data remains authoritative. Progress uses real value/max; radial progress derives its graphic from a numeric aria-valuenow through typed CSS attr rather than an independent visual number. Validate supplied percentages to 0–100, keep the written value and aria range consistent, and retain readable text if the graphic is unsupported. Updating actual progress still needs a data owner. Countdowns use time/tabular digits with a static label; CSS animation is not a wall clock or reminder service.

Input OTP stays one native text value with numeric inputmode, maxlength, pattern and autocomplete=one-time-code. It does not verify/send a code or auto-submit. File selection does not read, upload, store or expose the file to an agent. The native validation example uses a fictitious email, required/type constraints, :user-invalid and adjacent correction wording; browser validation remains authoritative. Real domain checks, server messages, error linking and asynchronous save outcomes require the app's validation contract. A valid example submission navigates to the same gallery through a native GET; it performs no database write.

Static alerts and toast examples do not announce fictitious live events. Actual live regions and notification lifetimes are supplied by the application when a real result occurs. Do not turn every passive sample into role=alert. Source examples are escaped before insertion into inspectable pre/code. Source snippets contain no script, inline event handlers or styles. This trusted gallery does not widen the Markdown element/attribute/URL allowlist or authorize arbitrary model HTML.

## Motion contract

The default design remains free of authored animation. Loading rotation and supplementary text rotation are explicit catalog opt-ins selected with visible native checkboxes; they are off initially. Spinner text remains present and the rotating layer is aria-hidden because complete wording is also persistent ordinary text. Loading uses a small 1s linear rotation; three text copies occupy separate thirds of a 9s loop with scoped delays. Hover/focus pauses text rotation, and unchecking immediately restores all static labels. A reduced-motion preference disables authored motion even when the checkbox is checked. The small noninteractive 3D tilt is available only for fine hovering pointers without reduced motion and has no continuous pointer-tracking script.

Native resizing can cause the browser itself to record a user-chosen width/height in an inline style. That is browser-owned state from an explicit resize action, not authored JavaScript styling; initial markup and shipped scripts remain free of style attributes/mutations.

Every animation property and each keyframe property has a ledger reason and user intent. Motion is supplementary and never changes domain state, live time, essential wording or permission. No page-wide animation, pulsing alarm, automatic carousel movement, hidden auto-dismiss or motion-only instruction is introduced.
